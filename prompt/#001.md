You are the Lead Game Engineer and Technical Architect responsible for building the first playable version of a browser-based fishing collection RPG.

Your job is to IMPLEMENT the project, not only propose ideas.

# 1. Product Vision

Build a web game about a child who dreams of becoming the greatest angler in the world.

The player begins in a small village with almost nothing.

The first accessible fishing location is a canal near the village.

Local villagers tell stories about a legendary fish that rules the canal.

The first chapter ends when the player successfully catches this local King Fish.

After that achievement, a scout / experienced angler notices the player's potential and invites them to travel to a larger fishing location.

The world should gradually scale like:

Village Canal
→ Mountain Stream
→ Large Lake
→ Major River
→ Coast
→ Ocean
→ Deep Sea
→ Mythical / legendary waters

Do NOT implement all of these now.

Chapter 1 is the only implementation target.

---

# 2. Game Identity

This is NOT:

* a business dashboard
* a generic React application
* a realistic fishing simulator
* a full MMORPG
* an open-world game
* a physics-heavy simulation

It should feel like a real digital game.

Core inspirations are:

* collection RPG
* training/run progression games
* fishing combat
* boss hunting
* equipment builds
* light narrative progression
* eventual asynchronous and multiplayer competition

The initial version must emphasize:

* satisfying interaction
* strong visual feedback
* readable game state
* collection
* progression
* anticipation when encountering rare fish
* excitement when fighting a King Fish

---

# 3. Technical Direction

Preferred stack:

* TypeScript
* React
* Vite
* PixiJS for gameplay rendering
* lightweight state management such as Zustand
* IndexedDB/local persistence for the first version
* Vitest for unit tests
* Playwright only where useful for critical flows

Do not introduce a backend yet unless the existing repository already requires one.

React is responsible for:

* menus
* HUD
* inventory
* collection
* shop
* dialog
* story UI
* equipment UI

PixiJS is responsible for:

* fishing scene
* fish movement
* fishing line
* water
* particles
* VFX
* camera movement
* screen shake
* frame-based animation

Do NOT render continuously moving gameplay objects through React DOM.

---

# 4. Architecture Principle

The most important architecture rule is:

CONTENT != GAME LOGIC != RENDERING

Keep them independent.

A new fish should normally require:

1. a fish content definition
2. relevant artwork/assets

It should NOT require modification of the fishing engine.

A new fishing area should normally require:

1. area definition
2. fish definitions
3. story/events
4. assets

It should NOT require rewriting existing gameplay systems.

Avoid premature abstractions.

Do not build systems that Chapter 1 does not need.

# 6. Data-Driven Content

Content must not be hardcoded into UI components.

BAD:

if (fishName === "snakehead") {
...
}

GOOD:

const fish = fishCatalog.get(id)

Fish definitions should contain data such as:

* id
* localized name
* description
* area
* tier
* rarity
* habitat
* active time
* preferred bait
* size range
* sell value
* behavior
* combat stats
* encounter conditions
* rewards
* collection metadata

Example conceptual model:

{
id: "moon-shadow-snakehead",

name: {
th: "พญาช่อนเงาจันทร์",
en: "Moon Shadow Snakehead"
},

area: "village-canal",
tier: 1.5,
rarity: "king",

habitat: ["deep-water"],
activeTime: ["evening", "night"],

stats: {
power: 72,
stamina: 85,
speed: 65,
technique: 80
},

behavior: "ambush-predator",

rewards: {
money: 2500,
reputation: 100
}
}

Exact balancing values may be adjusted during implementation.

# 7. Organizing Fish Collection

Do NOT use Tier folders as the main organization.

Use fishing area as the primary source folder organization.

Example:

content/fish/
village-canal/
mountain-stream/
emerald-lake/

Tier is metadata.

This allows querying:

* fish by area
* fish by tier
* fish by rarity
* fish by habitat
* fish by active time
* King Fish
* discovered / undiscovered fish

Create a centralized fish registry/catalog API.

UI must not need to know physical file paths.

# 13. Fishing Gameplay

Fishing must be interactive.

Do NOT implement:

gear score > fish score = automatic catch

Instead create a lightweight fishing combat system.

Core variables:

* fish stamina
* tension
* fish behavior
* equipment stats
* player actions
* timing
* fish distance / control state if useful

Possible player actions:

REEL
PULL
RELEASE
SKILL

Initial version may simplify this.

Main goal:

The player should constantly make small decisions during a fish fight.

---

# 14. Fishing State Machine

FishingSession should have an explicit state machine.

Suggested states:

CASTING
→ WAITING
→ BITE
→ HOOK
→ FIGHTING
→ CATCH

Failure states can include:

LINE_BREAK
FISH_ESCAPE

Keep state transitions explicit and testable.

Do not scatter fishing states across React components.

---

# 15. Smooth Runtime Requirement

Performance matters.

Do not push per-frame values through React state.

Keep things such as:

* fish position
* line physics/position
* particles
* water motion
* camera movement
* VFX

inside the rendering/gameplay layer.

React should receive lower-frequency semantic state:

* tension percentage
* fish stamina
* current action
* caught fish
* skill readiness
* session result

Aim for stable 60 FPS on an ordinary modern browser where practical.

Avoid unnecessary allocations in hot loops.

# 23. Content Validation

Implement a simple development-time content validator.

It should detect problems such as:

* duplicate IDs
* missing required fields
* invalid fish references
* invalid area references
* invalid gear references
* King Fish missing from catalog
* missing referenced assets where practical
* impossible unlock references

The game should fail clearly during development rather than silently accepting invalid content.

This is important because collection content may later be produced or expanded using AI-assisted workflows.

---

# 24. Tests

Prioritize unit tests around gameplay logic.

At minimum cover:

* tension calculations
* fishing state transitions
* fish stamina
* catch success
* failure states
* equipment modifiers
* fish registry
* content validation
* save/load serialization

Do not waste effort testing visual implementation details.

Critical game logic should be deterministic where possible by injecting seeded RNG.

# 25. RNG

* automated tests

# 32. Working Style

Prefer small, coherent patches.

For each meaningful task:

1. inspect relevant code
2. understand existing behavior
3. implement smallest correct change
4. run relevant tests
5. inspect side effects
6. fix regressions immediately
7. commit only logically complete work if repository workflow allows commits

Do not rewrite unrelated code.

Do not introduce architecture for hypothetical future requirements.

Do not change gameplay rules without documenting the reason.

---

# 33. Maintainability Rules

Prefer:

* small modules
* clear names
* explicit data
* pure functions for game calculations
* composition over inheritance
* reusable effects
* centralized schemas
* deterministic systems

Avoid:

* giant components
* giant global stores
* giant manager classes
* circular dependencies
* magic strings
* duplicated fish definitions
* switch statements containing every fish
* hardcoded content inside rendering code
* premature microservices
* unnecessary design patterns
